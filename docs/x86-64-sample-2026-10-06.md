## 2026-10-06 历史结论

wire **尚不支持 x86-64**。`PeFile::parse` 只接受 i386 / PE32；
CPU GPR、EIP、guest 地址、IAT、栈及 API gateway 均使用32位值和 x86 调用约定。
IR decoder 固定为32位模式，`.wir` v3 也没有64位目标标识。
本轮给 AMD64 文件增加明确的拒绝提示，未将导入信息的检查包装成执行支持。

## 单独扩展所需范围

1. 先建立独立64位目标 profile：PE32+ 头、64位 thunk/IAT、DIR64重定位、
   装载/卸载、TLS/TEB/PEB和高地址 guest VMM。保持 guest 地址与宿主指针的隔离及checked访问。
2. CPU/IR增加64位 GPR/RIP、REX、RIP-relative、扩展寄存器、I64算术及
   写32位寄存器清高32位的规则；8/16位写入和AH与REX互斥需差分验证。
   IR类型仍编进opcode，持久格式须记录目标架构并升级版本。
3. Windows x64 gateway和callback处理RCX/RDX/R8/R9、32B shadow space、
   栈对齐、栈参数、浮点参数及64位指针/结构。不能复用当前32位stdcall清栈机制。
4. 支持 `.pdata/.xdata` unwind 与64位异常结构，再用自编写的最小PE32+探针
   验证调用、DLL、内存、线程和异常；该Unity游戏作为后续真实兼容样本。
5. Unity/Mono引擎执行及 D3D11/DXGI/实际渲染路径另行推进，不能以EXE入口执行
   或UnityMain2被调用作为游戏已运行的验收。

64×8B的vreg bank仍可作为目标，但当前32位映射的0–7 GPR、8 EFLAGS和16–31
FP80槽不能原样容纳16个64位GPR。64位 profile需要版本化分配；例如0–15 GPR、
16 EFLAGS、17–23保留、24–39八组双槽FP80、40–63临时量。
这只是后续设计方案；当前完整512B bank本身也尚未实现。

按用户已有优先级，本轮继续解释器性能优化，未同时铺开64位/Unity功能实现。

## AMD64 基础检查点（2026-10-07）

新增 `src/x64/{memory,pe,cpu}.rs`，与 PE32 的 4GiB memory、CPU 与 `.wir` v3 分开。
稀疏 4KiB guest pages 只使用宿主数据 allocation，不创建可执行机器码；低 canonical user VA 上限 2^47，
完整范围/权限检查在读写前完成，跨页失败不提交半次写入。当前不包含 VMM guard/reserve/commit API。
PE32+ 所有 ImageBase、stack 和 IAT 目标保留 64 位；RVA 使用 32 位，导入/字符串/节/重定位有明确数量上限。
DIR64、8-byte name/ordinal thunk、重定位后按节权限映射已实现；TLS/delay import 明确拒绝。

整数 CPU 使用 iced 64 位 decode、16 GPR/RIP、REX、RIP-relative、GS base、I64/窄寄存器、
MOV/extensions/LEA、基本算术逻辑/条件分支与 CALL/RET/PUSH/POP；未实现指令在原 RIP 明确失败。
FLAGS 全量计算，不对 AMD64 做未经验证的丢弃；checked fault 不提交 GPR/RFLAGS/RIP/retirement。
按需逐字节取指，不因指令后的未映射页提前 fault。
Windows x64 整数/指针参数 helper 使用 RCX/RDX/R8/R9 与 RSP+40，返回只弹 8B return address。
还没有浮点 gateway、完整 callback/线程/异常 unwind、SIMD/x87、64 位 IR 或真实 DLL 装载执行。

六组基础回归通过：高地址映射/跨页写入原子性、真实 PE32+ fixture 的 DIR64/IAT、
64 位寄存器/RIP-relative 与 ABI shadow space、fault/页末取指、256 组 Unicorn 整数差分、CLI 高地址真实入口/未解决导入失败。
开发 oracle 仅使用现有 dev-dependency，没有将 QEMU/Unicorn 链进运行时。
